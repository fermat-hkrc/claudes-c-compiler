Issue Synopsis

narrow Phase 2 rewrites I64 bitwise ops to I32 without checking the use — I64 consumers get the zero-extended value (pipeline miscompile)

Expected behaviorpipeline preserves the interpreted value: sext(a)|sext(b) = -1 for (1,-1)
Observed behaviorOr rewritten to I32 with no re-extension; the I64 return reads 4294967295
Impact assessmentrun_passes(-O2, x86-64) compiles f(a,b){(i64)a | (i64)b} to return the zero-extended 32-bit Or: f(1,-1) = 4294967295 instead of -1
Minimal counterexamplef(a:i32,b:i32)->i64 { Or(sext a, sext b) at I64 } narrowed to Or@I32 with no re-extension; f(1,-1)=4294967295 != -1 (pipeline-confirmed)

Documentation: The cited documentation states this behavior IS handled; the code violates the document it ships with.

Author's text (verbatim): "narrows I64 bitwise operations (And, Or, Xor) to I32 when all operands are provably 32-bit values ... restricted to I32/U32 output to avoid sub-int register complications" — src/passes/README.md Integer Narrowing, Phase 2
