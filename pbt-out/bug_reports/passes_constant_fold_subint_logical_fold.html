Defect Report: constant_fold sign-extends sub-int operands before logical ops (LShr/UDiv/URem at I8/I16)

medium b1 round 07 — src/passes

Issue Synopsis

fold_binop's is_32bit fast path widens sub-int operands with as u32 (sign-extending a negative i8/i16 to 32 bits) before LOGICAL operations, so LShr/UDiv/URem at I8/I16 with negative constants fold to wrong values.

Expected behaviorLShr((I8)0xB8, 1) folds to 92 (logical shift of the 8-bit pattern)
Observed behaviorfolds to -36 (0xDC) — 0xFFFFFFB8 >> 1 low byte
Impact assessmentlatent silent miscompile: any I8/I16-typed logical shift / unsigned div / unsigned rem that reaches constant_fold folds wrong; narrow Phase 1 can create exactly those instruction shapes and the pipeline re-runs constant_fold afterwards
Minimal counterexampled = LShr(Const(I8(-72)), Const(I8(1)), I8) → fold gives -36, C11 requires 92

Contract basis: inferred — the IrType-typed BinOp semantics (the pass itself truncates operands to ty first, so the logical arms must zero-extend within ty's width too).

Remediation Strategy

In fold_binop's is_32bit logical arms, zero-extend the sub-int operand pattern to 32 bits (mask to the operand type's width before as u32); AShr's as i32 sign-extension is promotion-correct and can stay. Same fix for UDiv and URem arms. Red witness: src/passes/constant_fold.rs test_constant_fold_regression_subint_lshr_zero_extend (also covers UDiv).
