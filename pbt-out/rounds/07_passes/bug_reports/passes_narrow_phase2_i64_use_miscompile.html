Defect Report: narrow Phase 2 rewrites I64 bitwise ops to I32 without checking the use — I64 consumers get the zero-extended value

medium b2 round 07 — src/passes

Issue Synopsis

narrow_binops_without_cast rewrites an I64 And/Or/Xor with provably-32-bit operands down to I32 whenever the result has exactly one use — without checking whether that USE needs the full I64 value and without inserting a re-extension.

Expected behaviorf(a: i32, b: i32) -> i64 { (i64)a | (i64)b } evaluates to sext(a)|sext(b); f(1, -1) = -1
Observed behaviorafter run_passes(-O2, x86-64) the function is Or@I32 feeding an I64 Return with no Cast; f(1, -1) = 4294967295 (zero-extended)
Impact assessmentpipeline-level silent miscompile for any IR producer emitting the widen-widen-bitwise@I64 shape (And/Xor share the code path); violates the pass README's own "restricted to I32/U32 output" restriction, which the code enforces only for the rewrite TARGET, never for the output USE
Minimal counterexamplefn f(a,b)->i64 { Or(Cast a I32→I64, Cast b I32→I64, I64) }, f(1,-1) → 4294967295 instead of -1 (pipeline-confirmed)

Contract basis: documented — src/passes/README.md "Integer Narrowing" Phase 2 ("restricted to I32/U32 output") plus the pipeline's value-preservation contract.

Remediation Strategy

Before rewriting, verify the single use consumes the value in an I32/U32 context (BinOp/Cmp at target width, Cast to ≤32 bits, Store of ≤32-bit type); otherwise skip, or emit the re-extension (Cast target_ty→I64) after the narrowed op.
